# 四项短板的改进方案（阶段87）

按"预期收益 ÷ 改动成本"排序。每项都写了：根因 → 方案 → 要改哪里 → 工作量 → 风险 → 验收。

## P0 空结果任务做不出来（已解决，见阶段88）

> **实测结论（2026-11-24，已回滚）**：按原方案改 schema + prompt 后跑 8 个单元，结果 4/8（空结果仍 0/2，推荐单元回归 0/2）。日志显示模型直接输出 `{"citations": …}` / `{"answer": …}`，**缺 `{"name","arguments"}` 外层**——失败在解码层，不在载荷层。预声明的停止规则触发，改动已回滚（7 个文件哈希与冻结前一致）。详见 `docs/EMPTY_FINAL_V87.md`。
>
> **后续（阶段88）**：改用语法约束解码（lm-format-enforcer）强制工具调用信封，v1 把解析失败从 4 降到 0；v2 叠加"零结果提交空对象"后 **8/8 完成、解析失败 0**。空结果的通过是**结构性强制**（该步只有一个合法动作），不等于模型理解空结果。详见 `docs/CONSTRAINED_DECODING_V88.md`。

**现状**：阶段82 正式批次 6/8，两个失败都是 `e73-empty`（检索返回 0 篇、应提交空引用）。模型编造 `QZX_PAPER_1/2`、或输出裸 `citation` 数组，被拒后不改正。

**根因**：`final_answer` 要求模型自己构造 `{"citations":[]}`。对一个 1.5B 模型来说，"构造一个空数组并放进正确层级"比"判断没有结果"更难；而且这个动作和普通提交共用一个工具，模型没法表达"我确认没有结果"。

**方案**：新增一个**只在 returned=0 时可用**的工具 `submit_empty`，参数为空对象。

- 这是"给模型一个表达动作"，不是替模型补交：是否调用仍由模型决定，状态机只决定它此刻是否合法。
- 不改变普通提交路径，不放松任何校验。

**要改哪里**

| 文件 | 改动 |
|---|---|
| `gsearch/state_constraints.py` | `legal()`：当 `can_finish()` 且 `not returned` 时给出 `submit_empty`；`validate()` 拒绝任何参数；`observe()` 置 `finished` |
| `gsearch/constrained_agent.py` | `tools_for()` 增加一个 `@tool def submit_empty()`，走同一个 `client.call` |
| `research71/runner.py`（custom 路径） | 同上，确认使用的工具表 |
| `research71/prompts/custom.txt` | 加一句：检索为空时用 `submit_empty`，不要构造 `citations` |

**工作量**：半天（含测试与 8 次重跑）。**风险**：属协议变更，必须新冻结协议、不能与旧 6/8 直接比。

**验收**：`e73-empty` × 2 完成；其余 6 个单元不回归；差分测试证明"非空时 submit_empty 不可用"。

## P1 多轮与会话记忆（产品感知最强）

**现状**：一次任务一个 `ToolCallingAgent`，跑完即弃；追问只能重新提交一个新任务，模型看不到上一轮读过的论文。

**根因**：`research70/runner.py` 与 `research71/runner.py` 每次 `run()` 新建 agent；状态机 `ActionState` 也按任务新建；服务端 `jobs` 只是进程内字典。

**方案（分两步，先小后大）**

1. **MVP：基于已读论文的追问**（0.5–1 天）
   - 新端点 `POST /lab/jobs/{id}/followup`，带上一条 job 的 `read_ids` 与答案。
   - 用一次模型调用回答问题，**只能引用这些已读 ID**，不新增检索。
   - 前端在结果区加"追问"输入框，答案与引用追加到同一张卡片。
2. **完整会话**（2–3 天）
   - 会话对象持久化：`data/stage87-sessions/{id}.json`，含轮次、已读 ID、累计 token。
   - 每轮重置"动作预算"，但保留"已读/已返回"；跨轮禁止重复检索同一查询。
   - 会话预算：单轮 6 动作 / 7 步，会话累计 30 动作，超了明确拒绝。
   - SSE 事件带 `turn` 字段，刷新后按轮次恢复。

**风险**：上下文会随轮次增长（当前 30k 输入上限），必须做"只保留已读摘要 + 最近两轮"的裁剪；裁剪规则要写进协议。

**验收**：连续 3 轮追问，第 3 轮仍能引用第 1 轮读过的论文；断线刷新能恢复；超会话预算时拒绝且不丢历史。

## P2 写操作工具（收藏 / 笔记；不建议邮件）

**现状**：只有 `search_papers` / `recommend_papers` / `read_paper` 三个只读工具。

**方案**

| 工具 | 落点 | 备注 |
|---|---|---|
| `save_favorite(doc_id)` | 复用 `trialsite` 的偏好表（`/api/profile/feedback` 同一套 HMAC 访客身份） | 需要把实验室会话绑定到访客身份，否则写不进"我的收藏" |
| `save_note(doc_id, text)` | 复用 `trialsite/notebook.py`（FTS5、独立 CAS） | 纯文本、限长、转义 |
| 邮件/外部发送 | **不做** | 需要 SMTP 凭据、易被滥用；改为"导出 Markdown / 分享链接" |

**关键约束**

- 写工具必须**显式确认**：前端弹出"Agent 想收藏《…》，允许吗？"，确认后才执行。
- 写操作要进审计事件（谁、哪轮、改了什么），并且**不计入评价协议**，避免污染 6/8 那类完成率。
- 需要新的限流与幂等键，防止模型循环写。

**工作量**：1–2 天。**风险**：写操作一旦接错身份会写到别人的访客空间——必须用服务端签名身份，不信任前端传的 owner。

## P3 公开站接入 Agent（成本最高）

**现状**：8791 的公开站明确写"没有执行模型"；8802 只在本机跑。

**为什么不能直接搬**：万篇目录与画像来自 Scholar Inbox（CC BY-NC-ND），**不能公开部署**；1.5B 权重也不该进仓库。

**可行路径（建议选 2）**

1. 托管 10k 实验台：需要 GPU/CPU 主机 + 私有数据托管。许可上属于"非商业研究"灰区，不建议。
2. **公开站加"轻量 Agent"**：只跑在 167 篇公开目录上（arXiv CC0 元数据），工具只有 search/read/submit，模型可以用更小的 0.5B 或托管 API。合法、可部署、和"给朋友看的站"一致。
3. 浏览器端 BYOK：把用户自己的 key 放前端，泄露风险高，不适合公开。

**工作量**：3–5 天（新建 `deploy/stage87-agent` 复用 167 目录 + 工具层 + 预算 + 简单 UI + 部署）。**风险**：需要真实的托管资源；没有做过公网部署，首次上线要单独验收。

## 建议顺序与预期

| 顺序 | 项目 | 工作量 | 预期效果 |
|---|---|---|---|
| 1 | P0 `submit_empty` | 0.5 天 | 空结果单元可能从 0/2 到 2/2，整体 6/8 → 8/8 |
| 2 | P1-MVP 追问 | 0.5–1 天 | 从"一次性任务"变成"能接着聊"，体验提升最明显 |
| 3 | P2 收藏/笔记 | 1–2 天 | Agent 从"只读顾问"变成"能替你干活" |
| 4 | P1-完整会话 | 2–3 天 | 多轮真正可用（记忆、预算、恢复） |
| 5 | P3 公开轻量 Agent | 3–5 天 | 别人能直接用；需要托管资源与许可复核 |

## 统一要求（别跳过）

- 每一批改动都要**先冻结新协议**再跑：工具集变了，旧 6/8 与新结果不可直接比较。
- P0/P2 会改变"动作集合"，必须重跑差分测试与边界测试，保留全部失败。
- P3 之前要重新核一遍许可：公开站只能用 167 篇（arXiv 元数据），不要把 10k 目录、画像、用户轨迹带上去。
